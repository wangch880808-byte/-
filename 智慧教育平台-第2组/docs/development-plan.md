# 若依接入与后续开发路线

本轮仅完成架构准备，以下均为后续工作建议；不代表已经获得安装、导入基础工程、执行 SQL 或初始化 Git 的授权。

## 阶段一 范围和团队确认

- 评审原需求 P 分级与新方案 M 分级的差异，明确同步课堂、自建课程、AI 初评和答疑的实际首版承诺。
- 为九领域、前端、数据库及审核岗位指定具体成员，任务关联需求和验收条件。
- 确认教学班、试讲、成员变更、提交次数与迟交、成绩复核、统计口径、数据保留及第三方对接政策。

产物为确认的范围与责任记录，不以本轮文档中的建议默认替代学校决定。

## 阶段二 选择并接入真实若依工程

1. 核对 [官方 RuoYi-Vue 仓库](https://github.com/yangzongzhuan/RuoYi-Vue) 和所需前端来源，评估维护情况、部署环境、许可证及兼容性，记录选择的仓库、分支、标签或提交。
2. 根据真实上游兼容矩阵确定 Java、Spring Boot、Vue、Node 和已选择的 MySQL 的具体版本及其他运行环境；在决定之前保持版本未定，不沿用过时经验直接锁定。
3. 接入前重新备份当前正式文档与工作区。将上游后端聚合工程置于 `backend/`，唯一前端置于 `frontend/`；保留上游许可证、来源与本地修改记录。导入时合并已有 README 和领域规划，不覆盖它们。
4. 保留实际需要的 `ruoyi-admin/common/framework/system` 等原有模块；对 quartz、generator 或版本特有模块逐一核对用途与引用，不能仅删除目录使父 POM 失效。
5. 通过真实父 POM 和依赖管理创建/登记 `ruoyi-education`，核对包根、组件与 Mapper 扫描、安全上下文和业务接口入口位置，保证无循环依赖。
6. 将现有三端页面、API 和组件工作区融合到所选前端，复用原登录、请求客户端、路由权限与系统管理能力；不复制三个应用。
7. 确定数据库脚本来源及基线/增量分工，评审环境配置、密钥注入和测试数据；获得后续执行授权后再安装依赖、建测试库或初始化 Git。
8. 按真实工程执行基础构建与启动验证，再把经过验证的环境要求和命令写入 README；验证前不写“开箱可用”。

本阶段退出条件：来源、版本和许可证有记录，模块装配与三端基础身份经过验证，文档与实际路径一致。接入基础工程不等同于完成教学业务。

## 阶段三 领域和契约设计

完成核心实体、状态转换、权限矩阵、接口字段、目标与题目快照、提交/成绩版本、并发与幂等、统计口径及 SQL 评审。明确课件转换和实时同步的候选方案，以真实文件和教师 PC/学生手机验证可行性。

先建立跨班访问、隐藏答案、成绩发布、撤权及重复提交的验收案例，再按任务实现。接口规范见 [api-contracts.md](api-contracts.md)。

## 阶段四 按教学闭环实施

| 顺序建议 | 领域组合 | 阶段验收目标 |
|---|---|---|
| 1 | course、resource + 基础身份 | 教师建课，关联授权班级，学生访问授权资源；转换状态可见 |
| 2 | classroom + 前端三视图 | 教师演示、公开投影与学生同步页；重连恢复，私有数据隔离 |
| 3 | activity、assignment 基础提交 | 签到/实时题幂等，课堂小作业进入统一提交与批改链路 |
| 4 | prepare | 备课、预习、模板激活及课前诊断贯通 |
| 5 | assignment、learning | 作业改交、教师确认发布、错题和补学保留历史 |
| 6 | analysis | 原始指标、分母和样本可追溯，薄弱项回到下一轮教学草稿 |
| 7 | ai 及批准的增强能力 | 建议可追溯、权限隔离、失败可回退，按评审范围验收 |

此顺序参考新架构方案，未自动调整原需求承诺；若 AI 已被确认纳入首版，需相应并行安排，不直接后移。

## 阶段五 试点与交付

基于原需求第 11 章 AC-001～AC-008 与 V2.0 方案第 10 章八个场景形成追踪矩阵，覆盖跨班权限、预习、真实设备同步、签到答题、统一作业、评价错题、AI 失败和恢复演练。

原需求的 100 并发为试点估算，实际班级规模、P95、失败率与资源容量需重新确认，不能把本轮架构文档当作性能达标证据。试点前明确支持责任人、回滚和数据恢复方案，完成测试报告、操作说明与已知限制清单。
