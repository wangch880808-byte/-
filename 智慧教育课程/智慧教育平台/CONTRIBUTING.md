# 团队协作规范

当前处于正式开发前的准备阶段，尚未初始化 Git、指定成员或确定构建环境。下列分支与审核制度用于后续团队协作；实际仓库创建及默认分支设置需单独安排。

## 分支与提交

- 规划 `main` 为受保护的稳定主线，通过短期任务分支提交 PR；不直接向主线推送。采用其他发布模型时先记录决定。
- 分支名使用 `<type>/<domain>-<issue>-<summary>`，例如 `docs/architecture-12-api-contract`、`feat/activity-34-checkin`。示例编号不是已创建的任务。
- 类型包括 `feat`、`fix`、`docs`、`refactor`、`test`、`chore`；领域使用九个后端领域名、`frontend`、`sql` 或 `architecture`。
- 提交格式为 `<type>(<scope>): <简明说明>`，例如 `docs(architecture): 明确课堂公开数据范围`。一次提交表达一个目的，避免混入格式化与无关代码。
- 不强推共享分支，不重写他人提交，不提交构建产物、依赖目录、凭据或真实教学数据。

## 模块负责人

目前仅设置责任岗位，**具体人员均待项目负责人指派**。开工前在任务中登记负责人、协作者、审核人及交付范围；无人认领的模块不默认归任何成员。

| 工作范围 | 责任岗位 | 协作接口 |
|---|---|---|
| 若依选型、基础模块、安全与集成 | 技术负责人 | 所有领域、前端与部署 |
| course、resource | 课程与资源负责人 | 备课、课堂、作业、管理员端 |
| prepare、classroom、activity | 教学过程负责人 | 资源、作业、学生端、实时状态 |
| assignment、learning | 评价与学习负责人 | 题库、AI、学情 |
| analysis | 学情负责人 | 数据生产领域与统计口径评审 |
| ai | AI 适配负责人 | 备课、答疑、作业及数据权限 |
| 三端页面、公共组件与 API | 前端负责人，各端可指定协作者 | 对应业务负责人、基础权限负责人 |
| sql 与数据约束 | 数据库负责人 | 每个业务表的领域负责人 |
| docs 与 prototypes | 产品/架构文档负责人 | 原始需求、原型及接口审核人 |

模块负责人维护领域契约和文档，审核人负责独立复核；不将业务决定全部交给实现者自行解释。

## 开始任务

1. 阅读根 README、AGENTS、相关领域规划和两份外层来源，确认任务处于规划、开发或修复哪个阶段。
2. 关联需求编号，记录目标、所属领域、三端影响、接口/数据变更、验收条件与负责人。产品方案新增范围尚无需求编号时登记为待评审变更，不伪造原需求编号。
3. 需要跨领域协作时先约定数据归属、调用方向和返回内容，避免多人分别创建相同资源管理、提交引擎或权限逻辑。
4. 本轮不得创建业务实现。后续开始开发前应完成相应范围、基础工程与接口评审。

## 接口和数据库协作

- 以 [接口约定](docs/api-contracts.md) 为契约评审入口，先定义对象、权限、字段、状态、幂等、错误与示例，再分工实现。
- 前后端对字段类型、时间语义、分页结构、空值及 ID 表示达成一致；沿用最终若依响应结构，不自创三套请求格式。
- 教师、学生、管理员可调用同一业务服务，但响应字段和数据范围必须按权限裁剪，不能只在页面隐藏敏感字段。
- 变更接口时写明兼容策略、影响页面和消费者，由生产者与消费者共同审核；存在未合并依赖时在 PR 中链接，不以本地模拟结果当作联调通过。
- 数据库脚本进入 `sql/`，评审迁移顺序、唯一约束、快照版本、索引、数据影响与回退方案。不得把初始化脚本当作升级脚本反复执行。
- 未经授权不在共享环境执行数据库修改；本轮不提供或执行 SQL。

## PR 与代码审核

PR 说明应包含：具体问题及结果、需求/任务关联、涉及模块、接口与数据影响、验证结果、已知限制，以及界面变化的截图或原型引用。纯文档变更说明引用、路径和一致性检查即可，不编造测试报告。

合并前至少由一位独立审核人批准；跨领域变更还需涉及领域负责人共同审核。权限、正式成绩和数据库结构变更须由相应技术/业务/数据责任人复核。负责人尚未指派时先完成指派，再进行需其批准的合并。

审核重点：数据范围是否在服务端校验；状态转换是否明确；重复/并发请求是否正确；成绩和提交是否保留版本；投影与 AI 是否泄露私有内容；前端是否复用既有基础能力；文档是否正确区分规划和已实现。

相关检查通过、讨论解决且评审齐全后才能合并。没有 CI 时记录实际执行的人工检查；CI 建设后使用真实工具结果。缺少基础工程时，构建与业务测试应标为“尚不可执行”。

## 历史资产与需求变更

保留外层原始需求和 V2.0 方案。开发决策写入正式文档，不覆盖来源。删除历史资产须遵守 [迁移报告](docs/migration-report.md) 的最终确认流程。

需求优先级、成绩规则、数据保留、AI 服务、实时同步方式或基础版本改变时，记录动因、方案、影响、确认人和状态；审核通过再更新任务与验收条件。没有人员名单、技术版本或学校政策的事项明确标“待确认”，不得代填事实。
